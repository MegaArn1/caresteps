# demo-data

The fictional patient lives in code, not in a data file.

The seed is generated by [`app/demo/seed.py`](../app/demo/seed.py) and loaded with
`make seed`. It is code rather than a static dump for one specific reason: **the gaps
in the history are load-bearing.** A JSON snapshot would let someone edit a value and
silently remove the missing days that the demo depends on. Generating it means the
fixture either has the gaps or the seed fails loudly.

## The character

Mdm Tan, 72, with a fictional hypertension plan. Not a real person; not a real care
plan. Every inserted row carries `is_simulated = 1`, and the interface labels it.

## What the fixture deliberately contains

| Element | Why it exists |
|---|---|
| A three-day gap in readings | So the gap question has something real to be about |
| Two days with no medication report | Produces genuine `unrecorded` days, distinct from `not_taken` |
| One backfilled report | Shows the "I filled this in later" state, which is not the same as a normal report |
| One corrected reading | Proves the revision chain keeps the original rather than overwriting |
| One `unsure` report | Makes the four-state model visibly four states, not three |
| One open difficulty | Gives follow-up something real to follow up on |
| One resolved difficulty | Lets the demo show the app *not* re-raising a settled item |
| One chosen, completed action | Puts something in the "what you decided to do" section |
| Two consultation questions | Fills the appointment summary |

## Resetting

```bash
make seed     # drops every table and rebuilds from scratch
```

The same rebuild is reachable in the running app at `POST /api/demo/reset`, which is
what the "reset" control on the trace page calls. It only ever rebuilds simulated data.
